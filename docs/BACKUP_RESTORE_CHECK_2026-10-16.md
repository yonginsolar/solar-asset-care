## 이번 온라인 회귀

- 프런트엔드 기존 자동검사 83개에 백업 암호화 정상/변조/오류키 2개와 초안/저장 중 보호 5개를 추가해 90개 통과. TypeScript 검사 통과.
- 실제 Supabase Auth 토큰을 사용하는 역할/초기 비밀번호/최고관리자 검사 30개와 고객정보/동의/담당자 연결 검사 28개 통과.
- 기존 공개 배포본의 119개 업무 검사 통과. 7MB 업로드 6MB 중단·1MB 재개, 원본 무결성, 작은 미리보기, 전문가 판정, 사진 승인, PDF 보관·발행·회수, 3개 업체 견적, 인증서, 교차 조직·권한 회수·로그아웃 차단 포함.

- 위 업무 시험은 `example.invalid` 가상 계정과 별도 비운영 조직에서만 실행하고 파일·계정·조직을 정리했다. 실제 고객에게 메일을 발송하거나 기존 실제 회원의 권한을 바꾸지 않았다.
- 서버 로그 표본 25건은 의도적인 잘못된 입력/무권한/회수 접근 시험의 4xx 응답이며 Worker 실행 실패는 0건이다. 이 표본을 전체 기간 장애 없음의 증명으로 확대하지 않는다.
- Supabase 보안 진단은 기존 유출 암호 차단 미설정 경고 1건으로, 새 RLS/공개 테이블 경고는 확인되지 않았다. 이번 범위에서 유료 기능이나 인증 정책을 임의 활성화하지 않았다.

## 발견한 입력 유실 문제와 수정

공개 v16의 가상 고객으로 점검 목적을 바꾼 뒤 메뉴에서 ‘나의 현황’을 선택하자 확인 없이 양식이 사라지는 것을 재현했다. 발전소 등록/수정과 점검 접수/고객 의뢰 양식의 실제 필드값을 기준으로 미저장 입력을 보호하도록 보완했다. 기본값 그대로 조회하거나 원래 값으로 되돌린 경우에는 경고하지 않는다. 관리자의 기존 자산을 단순히 ‘수정’으로 열기만 한 경우도 저장 전 변경으로 계산하지 않는다.

메뉴 이동·상단 새로고침·로그아웃은 기존 확인창을 공유한다. ‘이어서 작성’을 선택하면 입력을 유지하며, 사용자가 명시적으로 버릴 때만 이동한다. 저장 중에는 ‘버리고 이동’으로 처리하지 않고 완료를 기다리도록 안내한다. 실제 브라우저 종료에는 기존 beforeunload 보호를 유지한다. 발전소/점검 제출의 동기 잠금과 처리 중 fieldset 비활성화도 추가해 중복 제출·저장 도중 입력 유실을 줄인다. 업무 저장을 자동 재시도하지 않는다.

이 수정은 해당 양식과 이미 보호하던 기본정보/약관/고객 양식, 공통 메뉴/새로고침/로그아웃에 대한 것이다. 모든 과거 양식·외부 이동·실제 모바일 OS 종료에서 영구 초안 자동저장을 제공한다는 뜻은 아니다. DB 스키마·기존 사용자 권한·운영자료를 바꾸지 않는다.

로컬 브라우저에서 320px 고객 화면으로 확인창 표시 → 이동 취소 → 같은 입력 유지, 상단 새로고침/로그아웃의 확인창, 점검 목적을 원래 값으로 돌린 뒤 경고 없이 이동, 발전소명 입력의 보호/취소/원상복귀를 확인했다. 시험 입력은 저장하지 않았고 콘솔 error는 없었다. 저장 중 보호와 여러 보호기의 우선순위는 별도 EventTarget 회귀로 검사했다.

최종 수정본은 기존 공개 범위를 유지한 v17, 소스 `76e462c62fb9a9df035f34a336083ca892c3d546`으로 2026-10-16 19:06 KST 배포 완료했다. 배포 ID는 `appgdep_6ad1f71dcd488191be43f2e39288319d`, 환경 설정 revision 2 유지다. 서버 비밀키를 프런트엔드 빌드에 복사하지 않았다. 이전 정상 v16을 보존하며 프런트엔드 원복 시에도 DB/권한 역마이그레이션을 하지 않는다.

v17 배포 후 119개 전체 업무 검사와 31개 게스트/PDF/비공개 경계 검사를 다시 통과했다. 온라인 고객 화면에서도 점검 목적 입력 → 이동 확인 → 취소 후 동일 입력 보존 → 원래 값 복귀 → 경고 없이 로그아웃을 확인했다. 검사 시 320px 문서 가로 넘침과 콘솔 error는 없었다. 실제 휴대전화 검수와 구분한다.

## 다시 점검하는 방법

필수: 기존 정상 Supabase CLI 로그인(현재 프로젝트에 대한 기존 권한), Node.js, 고정 CLI `2.121.0`, 로컬 PostgreSQL 17 도구. 새 PAT를 발급하거나 기존 인증을 바꾸지 않는다. macOS 기본 도구 경로 외에는 `SOLAR_PG_BIN`으로 설치된 PostgreSQL bin 경로를 지정한다.

`demo-site` 디렉터리에서 실행:

```sh
SOLAR_BACKUP_RESTORE_CHECK=1 node scripts/verify-backup-restore.mjs
```

이 명령은 **복구 점검 전용**이다. 실제 자료를 잠깐 비공개 임시 디렉터리에 보관하므로 권한 있는 담당자만 실행한다. 프로젝트와 허용 연결 호스트를 검사하고 모든 원격 DB 세션을 읽기 전용으로 제한한다. 새 로컬 서버는 네트워크 포트를 열지 않고 권한 0700 디렉터리의 Unix socket으로만 연결한다. 운영 DB/Storage에 쓰지 않으며 타 Supabase 프로젝트를 만들거나 과금 기능을 켜지 않는다.

실패하면 운영 복원/자동 재시도는 하지 않는다. 오류가 난 단계와 정리 결과를 확인한다. 프로세스를 강제 종료했으면 담당자가 `solar-restore-...`라는 **해당 실행의 정확한 임시 경로**와 그 클러스터 상태를 확인해 수동 정리한다. 다른 PostgreSQL 서버를 멈추거나 `/tmp` 전체를 지우지 않는다.

## 점검 통과와 별개로 남은 범위

1. **장기 보관 백업은 생성하지 않았다.** 시험키는 버리고 시험자료도 정리했다. 정기 백업 주기·보관 위치·보관 기간·복호화 키를 누가 안전하게 보유할지 확정해야 재사용 가능한 운영 백업을 구성할 수 있다. 이번 점검을 상시 자동백업 가동으로 표현하지 않는다.
2. 로컬 PostgreSQL에서 계정 행·비밀번호 해시·연결을 복원한 것이며, 별도 Supabase Auth 서버를 가동해 실제 로그인을 한 검증은 아니다. 재해 복구 시 구세션/refresh token의 취급을 결정하고, 안전한 재로그인/재설정 흐름을 검증한다.
3. Storage 바이트는 별도 로컬 파일에 복원했다. **다른 Supabase의 Storage API로 업로드하는 이전 시험은 하지 않았다.** 나중에 정상 Storage API로 bucket 설정과 경로를 먼저 만들고 파일을 업로드한 뒤 업무 DB 참조를 맞춘다. 운영 `storage.objects`에 직접 INSERT해 객체 복구를 대신하지 않는다.
4. Vault/암호화 root key, 공급자별 관리 스키마·크론 작업, SMTP/발신 도메인, 서버 비밀키, OAuth 설정, 배포 환경/DNS는 이 덤프만으로 복원되지 않는다. 실제 사용 여부를 대조해 별도 재연결한다. 이번 작업에서 root key·저장 암호·브라우저 쿠키를 추출하지 않았다.
5. 실제 초대/가입/복구 메일의 수신함·스팸함과 링크 클릭, iPhone/Android 실기기, 실제 열화상 원본 기반 오탐/정확도 검수는 별도다.

운영 복원이 필요하면 먼저 장애 원인과 대상/시점을 확정하고, 접근을 제한한 새 환경에서 이 순서로 검증한다: 스키마/권한 → Auth 식별자/업무자료 → 비공개 파일 → 설정/비밀값의 정상 재입력 → 관리자/전문가/고객·교차 조직 허용/차단 → 원본/발행 PDF 무결성 → 사용자 승인 후 전환. 현재 정상 운영 환경을 먼저 덮어쓰거나 기존 파일을 삭제하지 않는다.
