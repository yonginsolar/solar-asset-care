# 관리자 접근·초대 변경 기록

## 후속 점검: 현재 운영자료의 로컬 격리 복원

2026-10-16 후속 사용자 승인으로 실제 현재 DB 71개 테이블·346개 행, Storage 파일 8개의 백업/로컬 복원과 데이터·권한 대조를 완료했다. 아래의 ‘합성 복원만 확인/운영 복원 별도’ 기록은 당시 검증 범위이며, 최신 결과와 여전히 남은 새 Supabase Auth/Storage 전체 서비스 복구·장기 보관 백업 범위는 [백업·복구 점검](BACKUP_RESTORE_CHECK_2026-10-16.md)을 따른다. 기존 운영 환경을 덮어쓰거나 실제 사람에게 시험메일을 보내지 않았다.

## 후속 구현: 관리자 설정·고객 연결·역할별 포털

이 절은 아래의 이전 기록에서 제안/미구현으로 적었던 가입 정보·동의·고객 연결 상태를 대체한다. 이전 기록은 당시 시험 이력으로 보존한다.

- 공개 메인 `/`, 공통 로그인 `/login`, 고객 가입 `/signup`, 관리자 `/admin`, 전문가 `/expert`, 고객 `/client`, 적용 약관 열람 `/policy`로 분리했다. 로그인한 실제 멤버 역할을 확인한 뒤 맞는 포털로 안내하며 메뉴 숨김이 서버 권한 검사를 대신하지 않는다.
- 관리자는 운영주체 정식 명칭, 문의 이메일, 개인정보 담당 연락처, 이용약관과 개인정보 수집·이용 문안을 입력한다. 초안·미리보기와 실제 적용을 구분하고 적용본은 새 버전으로 불변 보관한다. 필수 항목 검사는 법적 적정성 검토를 대신하지 않는다.
- 실제 운영 조직은 운영주체가 아직 미정이므로 적용본 없이 유지했다. 관리자·전문가 기존 계정을 임의 동의 처리하지 않았다. 고객은 이메일 인증과 이름/연락처·고객 유형 입력을 완료해야 업무에 접근한다. 약관이 명시 적용된 뒤에는 관리자·전문가·고객 모두 본인의 기본정보와 현재 버전 동의가 필요하다. 이미 동의한 문안과 서버 시각을 이력에서 확인한다.
- 동의·개인정보·고객 연결은 서버 전용 테이블에 저장하고 RLS/직접 권한 회수로 보호한다. 공개 RPC는 invoker wrapper이며 내부 definer는 현재 Auth/이메일 인증/회원 상태/초기 암호/조직/역할을 확인한다. 기존 업무 RLS의 restrictive gate와 쓰기 트리거를 함께 적용해 구버전 definer RPC 우회도 막았다. 공개 열람은 현재 운영 조직의 적용본 문안으로 제한하며 초안·회원정보는 공개하지 않는다.
- 고객 유형은 개인·개인사업자·법인사업자다. 공통 이름·연락처와 사업자인 경우 상호/등록번호/대표자만 수집하며 주민번호·생년월일·가족·출자금·개인 은행계좌를 추가하지 않는다. 사업자등록번호 체크섬은 오타 검사이며 실재 사업자나 대표자 신원 확인이 아니다.
- 고객 관리에서 가입한 담당자의 신청정보를 확인하고 고객 레코드에 연결한다. 같은 번호를 입력했다고 자동 병합/승인하지 않는다. 연결한 발전소는 해당 고객의 활성 담당자가 조회하고 점검을 의뢰할 수 있다. 담당자/발전소 연결 해제는 공유 연결을 회수하며 원본을 삭제하지 않는다. 기존 개인별 발전소 권한은 별도이므로 자동 회수하지 않는다. 견적 요청의 최종 업체 선택 권한은 기존 지정 의뢰인 기준을 유지한다.
- 현재/대상 수정판을 비교해 고객 연결·설정의 오래된 저장을 거부한다. 중지된 담당자도 관리자가 공유 연결을 해제할 수 있으며, 중지 고객이 일반 가입 연결로 자기 상태를 다시 활성화할 수 없다.
- 전문가 포털은 배정 점검·자료·후보 판정·보고서 작성 중심이며 관리자 등록/최종 승인 기능은 제공하지 않는다. 고객 포털은 자기 또는 승인된 공유 발전소·점검 의뢰·진행 상태·발행 보고서·조치/견적 중심이다. 신규 등록과 관리자 입력을 할 수 없는 역할에는 비활성 관리자 입력 양식을 그대로 노출하지 않는다.
- 운영 이력은 같은 조직 관리자의 기존 감사 조회 권한으로 최근 100건을 읽으며 원래 감사 metadata/동의 본문/토큰을 화면에 풀어놓지 않는다. 외부 오류 수집 서비스를 새로 구매하거나 자료를 전송하지 않았다.
- 운영 설정/프로필/고객 등록의 실제 미저장 입력에만 이동 확인을 표시한다. 읽기·고객 선택·검색만으로 미저장 상태를 만들지 않는다. 기본정보와 동의 화면은 실패 시 입력을 보존하며 업무 저장·발송·권한 변경을 자동 반복하지 않는다.

### 남은 운영 입력과 검증 한계

운영주체·개인정보 연락처·실제 동의문과 보존/파기 기준은 관리자가 확정해 입력해야 한다. 원본 열화상과 촬영 조건을 통한 진단 정확도 검수, 실제 휴대전화 환경, 실제 운영 데이터/Storage/Auth 반환·복원 연습은 별도다. 임시 업로드나 개인정보를 임의 보존기간으로 자동 삭제하지 않는다. 이번 검증 결과를 외부 모니터링 서비스 도입이나 실제 자료 자동 파기의 승인으로 확대하지 않는다.

## 범위와 권한

사용자가 승인한 관리자 삭제, 민호 최고 관리자 보호, 최고 관리자 단일 양도, 초대 후 첫 비밀번호 생성 강제, 한글 초대메일 연결·지정 수신자 한 번 재발송을 구현했다. 유료 플랜·새 서비스 계정·도메인·DNS는 변경하지 않았다. 다른 조합 ERP 기능은 이번 구현 대상이 아니다.

## 현재 동작

- `minho@hoods.kr`는 기존 운영 조직의 유일한 최고 관리자다. 기존 정상 계정에는 첫 비밀번호 재생성을 요구하지 않는다.
- 최고 관리자의 역할 변경·중지·삭제는 서버 트리거로 거부한다. 공개 테이블에 사용자가 바꿀 수 있는 최고 관리자 플래그를 두지 않는다.
- 현재 최고 관리자만 같은 조직의 사용 중인 다른 관리자에게 권한을 양도할 수 있다. 현재 최고 관리자·대상 수정 시각을 재검사하고 조직/대상 행을 잠가 한 트랜잭션으로 단일 권한을 바꾼다. 이전 최고 관리자는 일반 관리자로 남아 이후 삭제할 수 있다.
- 관리자 삭제는 다른 일반 관리자의 작업공간 접근권한 해제다. 본인과 최고 관리자 삭제는 거부한다. 기존 Auth 계정, 발전소·점검·보고서와 작성 이력은 삭제하지 않는다. 삭제된 계정의 기존 토큰도 조직 자료를 읽거나 의뢰인 등록으로 우회할 수 없다.
- 최초 비밀번호 설정 여부는 서버 전용 `private.invited_password_setups`에 기록한다. 사용자 수정 가능한 메타데이터·브라우저 상태를 권한 근거로 사용하지 않는다.
- Supabase Auth는 초대 생성/확인 중 내부 무작위 암호를 만들거나 바꿀 수 있다. 단순 해시 존재/변경으로 완료 처리하지 않고, 이미 이메일 인증된 계정에서 이후 비밀번호가 실제 변경돼야 완료한다. 그 전에는 invited 상태를 유지하고 모든 기존 `private.has_org_role` 기반 업무 접근을 거부한다.
- 프런트엔드는 작업공간 조회 전에 서버 상태를 확인하며, 설정 전에는 비밀번호 생성과 로그아웃만 표시한다. 서버 상태 조회 실패도 차단한다. 사용자가 비밀번호를 저장한 뒤 계속하기로 재검사한다.
- 초대 대기 상태를 관리자가 화면에서 임의로 사용 중으로 전환하는 선택은 막았다. 서버의 비밀번호 선행 검사도 별도로 유지한다.
